# The app ships as a published Docker image

One operator runs one container. The page and the Node API ship together in a published image. The book stays on a named Docker volume at `/data`, as ADR 0002 records. An update pulls a new image and recreates the container with that same volume attached. Trades, closes, splits, listing names, deposits, starting cash, and a quote key saved from Admin survive the update. Deleting the volume is a separate start-over: cash returns to $100,000 and every listing is gone.

Every Docker name is `paper-portfolio`. The image is `ghcr.io/telagraphic/paper-portfolio`. The Compose project, the service, the container, and the volume are all `paper-portfolio`. The volume name is set explicitly, so Compose does not prefix it with the folder the stack runs from. The developer path and the consumer path therefore open the same book, and only one of them runs at a time because they share the container name and the port.

A multi-stage build produces the image. The build stage runs `npm ci` and compiles the Vite page and the TypeScript server. The run stage copies only the built `dist` tree. That works because the server imports nothing outside `node:` modules and this repository. A server change that adds a runtime npm package must also copy production `node_modules` into the run stage. Both stages use Node 24 slim, the version development and tests run on, pinned by digest so a rebuild gets the same base. The store depends on `node:sqlite`, which Node 22 only offers without a flag from 22.13, so Node 22 is not the floor.

The run stage creates `/data`, gives it to the `node` user, and then switches to that user. A new named volume copies that ownership on first mount. A volume created by the earlier root-run image stays owned by root, and the non-root server cannot write it. No operator runs that image yet. Whoever has a root-owned volume from development fixes it once with `docker run --rm -v paper-portfolio:/data alpine chown -R 1000:1000 /data`. The container listens on port 3000.

The server closes cleanly. On SIGTERM or SIGINT it stops accepting requests, closes the HTTP server, closes the SQLite store, and exits. `docker stop` then finishes at once instead of waiting ten seconds to kill a process that ignores the signal. `GET /api/health` answers 200 without reading the feed, because `GET /api/book` refreshes closes and spends feed requests. The image's `HEALTHCHECK` calls it with Node's own `fetch`, since the slim base has no curl. Docker Desktop shows the container as healthy once the book is open.

The EODHD key is environment configuration or a row in the book file. It is never copied into the image. `.dockerignore` keeps `.env`, `data/`, and SQLite files out of the build context. A key saved from Admin wins over `EODHD_API_KEY`. The variable is the fallback when Admin holds no key, so changing it does nothing while an Admin key exists. An Admin key is stored as plain text in the book on the volume. This amends ADR 0002, which kept the key only in the container's environment.

Two Compose paths share that layout. The developer path builds from this repository. The consumer path names the published image and does not need the source. Both publish `127.0.0.1:3000` only, set `DATABASE_PATH` to `/data/book.sqlite`, and mount the `paper-portfolio` volume on `/data`. There are no accounts. Anyone who can reach the port can trade, change the feed key, and read it back from the volume.

The schema carries its version in `PRAGMA user_version`. On open, the store applies every step above the file's version in order, inside one transaction, and then raises the version. Adding a table or a column is one step. A change that renames or reshapes a column is a step that rewrites the file in place. The existing check-then-`ALTER TABLE` for `opening_cash_usd` becomes the first numbered step. A file at a version newer than the image knows is refused, and the server exits with a message that names both versions. Pulling an older version tag after a newer one has migrated the book therefore stops instead of writing to a schema it does not understand. The way back is the backup taken before the update.

An update is four commands in the consumer folder: stop the stack, copy the book off the volume, pull, and start. The copy is `docker run --rm -v paper-portfolio:/data -v "$PWD":/backup alpine cp /data/book.sqlite /backup/book-YYYY-MM-DD.sqlite`, taken while the container is stopped so the file is not mid-write. The start is `docker compose pull && docker compose up -d`. Docker Desktop and lazydocker start, stop, and read logs. They are not the update path.

A GitHub Actions workflow builds and publishes the image to the GitHub Container Registry with buildx, for `linux/amd64` and `linux/arm64`. A pushed tag of the form `v1.2.3` publishes `1.2.3`, `1.2`, and `latest`. A pre-release tag such as `v1.3.0-rc.1` publishes only its own version and does not move `latest`. A push to `main` publishes nothing. The workflow runs typecheck and tests before it builds. The package is public, so pulling needs no login.

The operator README stays short: install Docker Desktop, save the consumer Compose file, start it, open `http://127.0.0.1:3000`, and follow the update commands, backup included. An empty `EODHD_API_KEY` is a valid first start. Admin can store a key afterward.

Shipping the repository and asking every operator to run `npm` and rebuild was the alternative. That keeps the book on the volume, but it makes every machine a build host and every design tweak a local compile. Baking the book into the image would give a blank slate on every pull and would erase history the operator meant to keep.
